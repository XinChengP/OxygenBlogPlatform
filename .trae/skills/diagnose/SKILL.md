# 系统化调试 (/diagnose)

## 概述

一个用于困难 bug 的规范流程。除非有明确理由，否则不要跳过阶段。

在探索代码库时，使用项目的领域词汇来获得清晰的心智模型，并检查你正在接触的区域的 ADR。

## 阶段 1 — 建立反馈循环

**这是核心技能。** 其他都是机械性的。如果你有一个快速、确定性、可自动运行的通过/失败信号，你就能找到原因——二分查找、假设测试和插桩都只是消耗这个信号。如果没有，盯着代码看再多也救不了你。

在这里投入不成比例的努力。**要积极，要有创意，不要放弃。**

### 构建反馈循环的方法 —— 大致按此顺序尝试

1. **失败测试** —— 在触及 bug 的任何接缝处（单元、集成、E2E）
2. **Curl / HTTP 脚本** —— 针对运行的开发服务器
3. **CLI 调用** —— 使用固定输入，将 stdout 与已知良好的快照对比
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，断言 DOM/控制台/网络
5. **重放捕获的跟踪。** 将真实网络请求/负载/事件日志保存到磁盘；在隔离中通过代码路径重放
6. **临时测试框架。** 启动系统的最小子集（一个服务，模拟依赖），用单个函数调用测试 bug 代码路径
7. **属性/模糊循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入寻找失败模式
8. **二分框架。** 如果 bug 出现在两个已知状态之间（提交、数据集、版本），自动化"在状态 X 启动，检查，重复"以便 `git bisect run`
9. **差异循环。** 在旧版本 vs 新版本（或两个配置）中运行相同输入并对比输出
10. **HITL bash 脚本。** 最后手段。如果必须人工点击，用脚本驱动他们，使循环仍有结构

构建正确的反馈循环，bug 就解决了 90%。

### 迭代循环本身

把循环当作产品。一旦有了循环，问：
- 能让它更快吗？（缓存设置，跳过无关初始化，缩小测试范围）
- 能让信号更清晰吗？（断言具体症状，而非"没崩溃"）
- 能让它更确定性吗？（固定时间，种子随机数，隔离文件系统，冻结网络）

30 秒的不稳定循环几乎等于没有。2 秒的确定性循环是调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。循环触发 100 次，并行化，加压，缩小时间窗口，注入睡眠。50% 的 flaky bug 是可调试的；1% 不是——持续提高率直到可调试。

### 当你真的无法构建循环时

停下来明确说明。列出你尝试过的。向用户请求：
- (a) 访问能复现它的环境
- (b) 捕获的工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制）
- (c) 添加临时生产监控的权限

**不要在没有循环的情况下进入假设阶段。**

## 阶段 2 — 复现

运行循环。观察 bug 出现。

确认：
- [ ] 循环产生**用户**描述的失败模式——不是恰好附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者，对于非确定性 bug，以足够高的率可复现）
- [ ] 你已捕获确切的症状（错误消息、错误输出、慢时间），以便后续阶段可以验证修复确实解决了它

在复现 bug 之前不要继续。

---

## 阶段 3 — 假设

在测试任何假设之前生成**3-5 个排序的假设**。单一假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它做出的预测。

> 格式："如果<X>是原因，那么<改变 Y>会让 bug 消失/<改变 Z>会让它更严重。"

如果你无法陈述预测，这个假设就是直觉——丢弃或完善它。

**在测试前向用户展示排序列表。** 他们经常有能立即重新排序的领域知识（"我们刚部署了 #3 的更改"），或知道他们已经排除的假设。便宜的检查点，巨大的时间节省。如果用户不在，用你的排序继续。

---

## 阶段 4 — 插桩

每个探针必须映射到阶段 3 的特定预测。**一次改变一个变量。**

工具偏好：
1. **调试器 / REPL 检查** 如果环境支持。一个断点胜过十个日志。
2. **目标日志** 在区分假设的边界处。
3. 永远不要"记录所有然后 grep"。

**给每个调试日志打标签**，用唯一前缀，如 `[DEBUG-a4f2]`。最后清理变成单次 grep。没标签的日志会存活；有标签的会死。

**性能分支。** 对于性能回退，日志通常是错的。相反：建立基线测量（时间框架、`performance.now()`、分析器、查询计划），然后二分。先测量，后修复。

---

## 阶段 5 — 修复 + 回归测试

**在修复之前写回归测试** —— 但前提是存在**正确的接缝**。

正确的接缝是一个测试能在调用点练习**真实 bug 模式**的地方。如果唯一可用的接缝太浅（单调用者测试当 bug 需要多调用者，单元测试无法复现触发 bug 的链），那里的回归测试会给出虚假信心。

**如果不存在正确的接缝，这本身就是发现。** 记下来。代码库架构正在阻止 bug 被锁定。标记到下一阶段。

如果存在正确的接缝：
1. 将最小化复现变成该接缝处的失败测试
2. 观察它失败
3. 应用修复
4. 观察它通过
5. 针对原始（未最小化）场景重新运行阶段 1 反馈循环

---

## 阶段 6 — 清理 + 事后分析

声明完成前必须：
- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或缺少接缝已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 临时原型已删除（或移到明确标记的调试位置）
- [ ] 正确的假设在提交/PR 消息中说明——以便下一个调试者学习

**然后问：什么能防止这个 bug？** 如果答案涉及架构改变（没有好的测试接缝、纠缠的调用者、隐藏耦合），在修复完成后交给架构改进流程。在修复完成后提出建议，而非之前——你现在比开始时掌握更多信息。

## 使用示例

**你：** /diagnose 文章评论提交后有时不显示

**我：** 好的，让我们系统化调试。

**阶段 1 — 建立反馈循环**

首先，我需要构建一个能复现这个 bug 的循环。让我检查现有测试...

[探索代码]

我会创建一个测试脚本来模拟评论提交：

```bash
# scripts/test-comment.sh
curl -X POST http://localhost:3000/api/blogs/test-post/comments \
  -H "Content-Type: application/json" \
  -d '{"content":"测试评论","author":"测试用户"}'
```

运行 10 次... 复现率约 30%。让我提高它...

[添加并行请求]

现在复现率 80%，可以调试了。

**阶段 2 — 复现**

确认症状：评论提交返回 200，但 GET 列表中不出现。

**阶段 3 — 假设**

我的排序假设：
1. 缓存问题 —— 评论写入了但缓存未失效
2. 竞态条件 —— 并发写入覆盖了数据
3. 数据库事务问题 —— 提交未真正提交

**阶段 4 — 插桩**

在评论提交和查询处添加日志...

[DEBUG-1a2b] 评论写入: id=123
[DEBUG-1a2b] 缓存失效: key=comments:test-post
[DEBUG-1a2b] 查询评论: postId=test-post, found=0

**阶段 5 — 修复**

发现：缓存失效在事务提交前执行。修复：移动缓存失效到事务后。

写回归测试...

**阶段 6 — 清理**

移除所有 DEBUG 日志，提交修复。

## 何时使用

✅ **必须使用：**
- 难以复现的 bug
- 性能回退
- 生产环境问题

❌ **不需要：**
- 明显的语法错误
- 简单的逻辑错误
