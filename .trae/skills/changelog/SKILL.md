# 更新日志管理 (/changelog)

## 用途

当你需要：
- 记录代码层面的功能变更或技术实现调整
- 创建符合规范的更新日志文件
- 整理版本发布说明和系统架构变更
- 为变更日志页面生成新的技术条目

**不包括：** 个人动态发布、博客文章发布、内容文本编辑等纯内容类更新

## 更新日志规范

### 文件位置与命名

更新日志存储在 `src/content/changelogs/` 目录中，文件命名为 `YYYY-MM-DD.md`。

### Frontmatter 格式

```markdown
---
date: "YYYY-MM-DD"
title: "更新标题"
type: "feature|optimize|fix|docs|style|refactor"
commits:
  - "commit message 1"
  - "commit message 2"
---
```

### 类型说明

代码中严格定义了六种类型，无其他选项：

| 类型 | 中文标签 | 颜色 |
|------|---------|------|
| feature | 新功能 | #66ccff (天依蓝) |
| optimize | 优化 | #9966ff (紫色) |
| fix | 修复 | #ff66cc (粉色) |
| docs | 文档 | #ff9966 (橙色) |
| style | 样式 | #ccff66 (黄绿色) |
| refactor | 重构 | #66ff99 (绿色) |

### 旧类型映射

代码读取时会将旧类型自动映射到上述六种之一：

| 旧类型 | 映射目标 | 说明 |
|--------|---------|------|
| perf | optimize | 性能优化类提交映射为优化 |
| chore | docs | 其他/杂项类提交映射为文档 |

**注意：** 若 frontmatter 中的 type 值不在有效列表中且无法映射，代码会默认将其视为 `docs` 类型。

### 内容结构模板

```markdown
## 功能概述

用一两句话概括本次更新的核心内容和目标。

## 主要变更

### 功能/模块名称

- **改动点名称**：具体描述该改动的内容和效果
- **另一改动点**：具体描述

### 另一功能/模块

- **改动点**：描述

## 技术实现

| 文件路径 | 说明 |
|---------|------|
| `src/...` | 改动说明 |

## 使用方式

### 功能名称

1. 操作步骤一
2. 操作步骤二

## 注意事项

- 需要注意的事项一
- 需要注意的事项二
```

**格式说明：**
- 概述标题使用 `## 功能概述` 或 `## 更新概述`
- 变更容器使用 `## 主要变更` 或 `## 主要更新`
- 分类标题使用 `### 功能/模块名称` 按模块分组
- 列表项使用 `**加粗前缀**：详细描述` 格式
- 技术实现部分用表格列出关键文件路径和说明
- 使用方式部分用编号列表或代码块说明操作步骤
- 注意事项部分列出兼容性、配置等需要注意的点

**可选补充部分（根据内容需要灵活添加）：**
- `## 影响范围` —— 说明变更影响的功能或页面
- `## 优化效果` / `## 性能提升` —— 说明优化带来的效果
- `## 导航结构变更` —— 导航或路由结构调整时说明变更前后对比
- `## 相关功能` —— 说明与本次变更相关的其他功能

## 成就标签系统

代码中定义了四种成就类型，自动根据提交数量和日志行数计算：

| 成就名称 | 触发条件 | 颜色 |
|---------|---------|------|
| 略感疲惫 | 关联提交数量 >= 10 且 < 20 | #7366ff |
| 肝爆了 | 关联提交数量 >= 20 | #e566ff |
| 麻雀虽小五脏俱全 | 关联提交 = 1 且 日志行数 > 55 | #ff66a6 |
| 人声鼎沸 | 预留成就类型 | #ff9966 |

支持在日志 frontmatter 中手动配置荣誉：
```yaml
honors:
  - name: "自定义荣誉名称"
    color: "bg-gradient-to-r from-blue-500 to-purple-500"
```

## 工作流程

1. **确定日期** —— 使用今天或发布日期作为文件名
2. **确定类型** —— 根据主要变更选择最合适的类型（新功能/优化/重构/修复/样式/文档）
3. **收集提交** —— 列出相关的 commit message
4. **编写概述** —— 用一两句话概括本次更新的核心内容和目标
5. **分类变更** —— 按功能模块或组件划分子分类，使用 `###` 标题
6. **描述改动** —— 在每个分类下用 `**加粗前缀**：详细描述` 格式列出具体改动
7. **补充技术实现** —— 用表格列出关键文件路径和对应说明
8. **添加使用方式** —— 如有新功能或重要交互变更，用编号列表说明操作步骤
9. **标注注意事项** —— 列出兼容性、配置、数据等需要用户注意的点
10. **可选扩展** —— 根据需要补充影响范围、优化效果、导航结构变更等部分

## 使用示例

**你：** /changelog 记录今天的拼音转换器增强功能

**我：** 好的，我将根据项目规范创建更新日志文件...

```markdown
---
date: "2026-04-29"
title: "拼音转换器增强功能"
type: "feature"
commits:
  - "feat(pinyin): 添加ü/v格式切换功能"
---

## 功能概述

为拼音转换器添加 ü/v 格式切换功能，满足用户在不同场景下的拼音输出需求。

## 主要变更

### ü/v 格式切换功能

- **新增选项**：在转换选项区域添加"ü 显示格式"切换按钮
- **支持两种格式**：
  - `ü` 格式：传统的拼音符号显示（如：lǜ、nǚ）
  - `v` 格式：电脑输入法常用的 v 替代显示（如：lv、nv）
- **实时切换**：选择格式后即时生效，无需重新输入
- **布局优化**：将选项网格从 4 列调整为 5 列，使所有选项整齐排列

## 技术实现

| 文件路径 | 说明 |
|---------|------|
| `src/app/tools/pinyin-converter/page.tsx` | 添加 uFormat 选项、convertUFormat 转换函数和 UI 控件 |

## 使用方式

1. 进入拼音转换器页面
2. 在"转换选项"区域找到"ü 显示格式"选项
3. 点击 `ü` 或 `v` 按钮切换显示格式
4. 输入中文文本即可看到对应格式的拼音输出

## 注意事项

- 默认使用传统的 `ü` 格式显示
- 切换格式后，已输入的文本会自动重新转换
- 该设置仅在当前会话有效，刷新页面后恢复默认
```

## 何时使用

✅ **推荐使用：**
- 完成代码功能开发后记录技术变更
- 发布版本前整理系统更新说明
- 需要按规范生成新的日志文件
- 整理一段时间内的架构或技术变更

❌ **不推荐使用：**
- 发布新的个人动态（moments）
- 发布新的博客文章（blogs）
- 仅修改了文本内容或错别字
- 临时调试代码，不会合并到主分支
- 个人本地实验性改动
