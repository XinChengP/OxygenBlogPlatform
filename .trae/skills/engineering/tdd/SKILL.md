# 测试驱动开发 (/tdd)

## 核心理念

**测试应该验证行为，而非实现细节。**

代码可以完全改变；测试不应该变。

**好的测试：**
- 通过公共接口测试真实代码路径
- 描述系统**做什么**，而非**怎么做**
- 读起来像规格说明："用户可以提交有效评论"
- 重构时不会失败

**坏的测试：**
- 与实现耦合
- 测试私有方法
- 通过外部手段验证（如直接查询数据库而非使用接口）
- 重构时失败但行为未变

## 反模式：水平切片

**❌ 不要一次性写所有测试，再写所有实现**

这是"水平切片"——把 RED 当作"写所有测试"，GREEN 当作"写所有代码"。

这会产生糟糕的测试：
- 批量写的测试验证的是**想象的**行为，而非**实际的**行为
- 你最终测试的是事物的**形状**（数据结构、函数签名）而非用户可见的行为
- 测试对真实变化不敏感——行为坏了它通过，行为正常它失败

**✅ 正确做法：垂直切片（追踪弹）**

```
错误（水平）:
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流程

### 1. 规划阶段

在探索代码库时，使用项目的领域词汇，尊重该区域的 ADR。

写代码之前：
- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测试哪些行为（优先级排序）
- [ ] 识别[深度模块](deep-modules.md)的机会（小接口、深实现）
- [ ] 为[可测试性](interface-design.md)设计接口
- [ ] 列出要测试的行为（不是实现步骤）
- [ ] 获得用户对计划的认可

**问：** "公共接口应该是什么样的？哪些行为最重要需要测试？"

**你无法测试所有东西。** 与用户确认哪些行为最重要。把测试精力放在关键路径和复杂逻辑上，而非每个边界情况。

### 2. 追踪弹（第一个测试）

写一个测试，验证系统的一个行为：

```
RED:   写第一个行为的测试 → 测试失败
GREEN: 写最小代码让它通过 → 测试通过
```

这是你的追踪弹——证明端到端路径可行。

### 3. 增量循环

对每个剩余行为：

```
RED:   写下一个测试 → 失败
GREEN: 最小代码让它通过 → 通过
```

规则：
- 一次一个测试
- 只写足够通过当前测试的代码
- 不要预测未来的测试
- 保持测试聚焦于可观察行为

### 4. 重构

所有测试通过后，寻找[重构机会](refactoring.md)：
- [ ] 提取重复代码
- [ ] 深化模块（把复杂性隐藏在简单接口后）
- [ ] 自然的地方应用 SOLID 原则
- [ ] 考虑新代码揭示了现有代码的什么
- [ ] 每次重构步骤后运行测试

**不要在 RED 时重构。** 先达到 GREEN。

## 每轮检查清单

```
[ ] 测试描述行为，而非实现
[ ] 测试只使用公共接口
[ ] 测试会在内部重构中存活
[ ] 代码对这个测试是最小的
[ ] 没有添加推测性功能
```

本项目使用：

- **React Testing Library** - React 组件测试

## 使用示例

**你：** /tdd 我要实现文章评论功能

**我：** 好的，让我们用 TDD 开发。

首先，规划阶段：

**接口设计：**
- `POST /api/blogs/[slug]/comments` - 提交评论
- `GET /api/blogs/[slug]/comments` - 获取评论列表

**要测试的行为（按优先级）：**
1. 用户可以提交有效评论
2. 空评论被拒绝
3. 评论成功后会显示在列表中
4. 评论按时间倒序排列

你觉得这个计划如何？需要调整吗？

**你：** 可以，开始吧

**我：** 好，开始第一轮 RED→GREEN。

**RED：** 写第一个测试——用户可以提交有效评论...

[测试代码]

运行测试... 失败（预期，还没实现）

**GREEN：** 写最小实现...

[实现代码]

运行测试... 通过！

进入下一轮...

## 何时使用

✅ **推荐使用：**
- 开发核心业务功能
- 修复复杂 bug
- 需要高置信度的代码
- 接口设计需要仔细思考

❌ **不推荐使用：**
- 简单的 UI 调整
- 一次性的脚本
- 探索性原型
